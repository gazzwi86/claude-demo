# Council Review — the Claude Code harness

Reframed for the *harness*, not the app underneath. The music-looper at
`apps/` is the substrate Claude exercises; this report asks whether the
`.claude/` config around it is fit-for-purpose as **an onboarding /
demo / learning artefact for engineers configuring Claude Code**.

The previous app-focused review is in this repo's git history at commit
`7146a99`'s parent's terminal output (pre-pivot); the action items
that survived the pivot are summarised at the end of this document.

---

## Executive answers

### 1. Is this an effective vehicle for onboarding engineers to Claude Code config?

**Mostly yes, with two real gaps.** The repo does demonstrate every
major Claude Code primitive — settings, hooks, rules, commands, agents,
skills, plans, per-package `CLAUDE.md`. Each one has at least one
working example. The plan file at
`.claude/plans/the-project-itself-meaning-precious-valiant.md` is
particularly strong: a real plan that drove real commits, with the MCQ
decision-taking visible.

The two gaps:

- **The wiki / anatomy / graph trio is half-built.** `docs/wiki/` pages
  exist but are stale-marker stubs (the rewrite never ran `/anatomy
  refresh`). `ANATOMY.md` is a placeholder. `graphify` was never run on
  the new monorepo. The hook *infrastructure* for the wiki is sound
  (`area_for_path` + `mark_anatomy_stale`), but a new engineer landing
  here today won't see the **payoff** — populated, useful wiki pages
  they'd actually navigate before grepping. **First action of the next
  session: generate them.**
- **Tests cover the dispatcher, not the audit skills.** `hooks_test.py`
  proves `area_for_path()` and the Stop drift detector work, but
  there's no end-to-end test that, say, `/cc-audit` or `/anatomy`
  actually do anything against this repo. The harness has unit tests;
  it doesn't have integration tests.

### 2. Will engineers see the benefit of the LLM wiki, anatomy file, and graph?

**Not yet.** The plumbing is in place; the demonstrated value isn't.
Concretely:

- `docs/wiki/api-routes.md`, `web-audio.md`, `web-pages.md`, `shared.md`
  etc. exist but most contain only stale markers like `<!-- stale:
  apps/web/lib/audio/engine.ts --> <!-- at: 2026-05-08T... -->`. A
  reader sees no actual content — they see a TODO list.
- `ANATOMY.md` has a stub tree from Phase 1 plus the words
  `_Stub — will be regenerated by /anatomy once Phase 8 lands._` Phase
  8 landed; `/anatomy` was never invoked.
- `graphify-out/` doesn't exist; the `pre-tool-use graphify-hint` hook
  is dormant.

The hook chain *would* work the moment someone runs the slash commands.
The next session needs to do that, then commit the populated state, so
the demo audience sees the artefact (not the placeholder).

### 3. Are hooks / rules / settings.json / agents / commands / skills / CLAUDE.md right for the app?

**Mostly right; one structural change is needed.** Per-area:

- **Hooks** (`scripts/hooks.py`): right shape — single dispatcher, all
  events landing in one auditable file. The `check_no_secrets` regex is
  noisy (caught a fixture password in tests three times during the
  rewrite, forcing extraction to consts). Worth tightening, or
  whitelisting `tests/*.test.ts`.
- **Rules** (`rules/*.md`): four flat rules files. **They should be
  path-globbed.** Today, the testing rule applies repo-wide; in
  practice, `apps/api/tests/` and `apps/web/tests/` use different
  runners and patterns. Path-glob support would let
  `apps/api/tests/*.test.ts → testing-fastify.md` and `apps/web/**/*.test.tsx → testing-rtl.md`.
- **`settings.json`**: comprehensive. Hooks for 9 events, permissions
  in three buckets, env vars, MCP server. The inline `prompt:` LLM hook
  next to the `command:` hook on the same matcher is itself a teaching
  point — shows two ways to do the same thing.
- **Agents** (`agents/*.md`): two minimal agents (`api-designer`,
  `test-writer`). Enough to demonstrate registration; not enough to
  demonstrate the multi-agent collaboration pattern. The agent-teams
  experiment in this rewrite *failed* (permission prompts didn't
  surface to the user); that failure is itself good demo material.
- **Commands** (`commands/*.md`): five commands, each narrow and
  scaffolds-shaped. `/add-endpoint` and `/check-health` were exercised
  during the rewrite. Good as is.
- **Skills** (`skills/`): only `20-questions`. Thin compared to the
  user-level skills visible at session start (`cc-audit`, `frontend-design`,
  etc.). **Worth shipping a project-specific skill** — e.g. `/looper-add-effect`
  that scaffolds a new EffectsRack node + slider + engine wiring.
- **`CLAUDE.md`**: top-level + per-package (`apps/web/CLAUDE.md`,
  `apps/api/CLAUDE.md`, `packages/shared/CLAUDE.md`, `infra/CLAUDE.md`).
  Right structure. The user has correctly identified that
  **finer-grained CLAUDE.md (per-area, e.g. `apps/web/lib/audio/CLAUDE.md`)** would help — see Next Steps.

### 4. Do the tests prove useful for the audit skill / hooks config?

**They prove the dispatcher's correctness; they don't prove the audit
loop works.** The 35 hook tests are a real asset — they caught the
`area_for_path` "len(parts) >= 4" regression during the rewrite. But:

- There's no test that runs `/cc-audit` against this repo and asserts
  the output finding count is non-zero / contains expected categories.
- There's no test that runs `/anatomy refresh` and asserts the wiki
  pages get populated with file lists + signatures.
- There's no test that the PostToolUse `claude-review` (Opus -p) hook
  actually surfaces a finding when fed a deliberately bad diff.

These are integration tests, not unit tests, and they'd be more
expensive to run in CI. But for a *demo / learning* repo, they're
exactly what shows engineers "yes, this stuff works." Worth adding even
if they're skipped on CI by default.

## Persona briefs (reframed for the harness)

### Senior frontend engineer

The split between `CLAUDE.md` (architecture) and `rules/code-style.md`
(formatting) is the right separation. But the `.claude/` config doesn't
encode that React components have *different* conventions than Fastify
routes — both pull from the same `code-style.md`. **Path-glob the rules
files** so `apps/web/components/*.tsx` gets a component-conventions rule
that doesn't apply elsewhere. Today every rule is global.

The PostToolUse `claude-review` hook (the inline `prompt:` one) is doing
double work with the command-based `claude-review` hook on the same
matcher. Pick one. The inline `prompt:` is opaque to the user; the
command-shelled one runs `claude -p` async and is at least debuggable.

**First change:** move `rules/*.md` to a path-globbed model.

### Senior backend engineer

The hooks-as-deterministic-enforcement pattern is the most
underappreciated part of this repo. `check_no_secrets` enforces the
"no hardcoded secrets" *rule* by making it a hook — Claude literally
cannot ship a secret-containing file. That's better than rule text,
which Claude might forget.

The current rule files describe behaviour Claude should follow; only
one of them (`security.md`) has a hook backing. **Backfill hooks for
the testing and code-style rules** — e.g. a PostToolUse hook that runs
`prettier --check` on the touched file and blocks on diff. It'd
catch tabs-vs-spaces drift before commit.

**First change:** make the relationship "rule + optional hook
enforcement" explicit in `rules/README.md`, and add a hook for one more
rule to demonstrate the pattern.

### Senior devops engineer

The `git-hooks/` directory is wired through `core.hooksPath` by `/setup`

which exits 1 with a list of stale files. **That's the gate that
prevents the wiki from rotting**, and it's the lever the next session

`.claude/scripts/setup-graphify.sh` exists and `/setup graphify`

`settings.json` ships permissions; `settings.local.json` ships dev

**First change:** run `/setup graphify` and commit `graphify-out/`.

### Andrej Karpathy

The pedagogical value here is in **the dispatcher pattern**. One
`hooks.py` file handles every hook event. A student can read the
whole thing in one sitting, trace what fires when, and understand
how Claude Code works under the hood. Compare to the alternative —
ten separate hook scripts — which would scatter the mental model.

The `area_for_path` function is a teaching artefact about path-based
config. Five lines of pattern matching, one regex normalisation,
testable in isolation. I'd point a student at it before
`mark_anatomy_stale` because the latter has IO and the former is pure.

The plan file is the most honest thing in the repo. It shows what
Claude proposed, what the user disagreed with via MCQ, and what got
written. Most "AI-built" code hides this; here it's preserved.

**First change:** a single one-pager in `.claude/README.md` (already
written above) explaining what each subdirectory is for. Don't make
students reverse-engineer the mental model.

### Boris Cherny

The Plan-mode → Execute split worked here. The plan file outputs are
durable; reading the plan tells you the intent of the codebase faster
than reading the code.

What didn't work: agent teams + worktrees. Two teammates spawned with
`isolation: "worktree"` blocked on permission prompts that didn't
surface to the user; both stalled. The work fell back to the
orchestrator. **This is itself a demo-worthy moment** — show the team
config at `~/.claude/teams/music-looper-build/config.json` and the
actual transcript of the failure. Honest demo > polished demo.

The hook system caught real things in this rewrite (the fixture
password). That earned the configuration its place. But the
`check_no_secrets` regex is naive — it false-positives on
`password: "wrong-password"` and forces extracting fixture passwords
to consts. Tightening the regex to skip `*.test.ts` (or matching only
common secret formats) would reduce friction without losing the
catch.

**First change:** narrow `check_no_secrets` to ignore obvious test
fixtures.

### Security engineer

The `.claude/` config is **the security gate** for this repo, more so
than the app code. `check_no_secrets` enforces the "no committed
secrets" rule deterministically; Claude can't bypass it. The
PostToolUse `prompt:` hook shells out to Claude itself for a
security-linter pass. That's a defense-in-depth stack.

But: the secret scanner is regex-only. It misses entropy-based
secrets (random hex strings) and matches on common-word collisions.
Pair it with `gitleaks` or a config-driven allowlist. The `cc-audit-security`
skill (visible at session start) flags this exact pattern.

`settings.json` `permissions.deny` blocks `rm -rf *` and `curl*` and
reads of `*.env` / `*.pem` / `*.key`. Good list, but it's a small one
— a real production setup would include allowlist-by-default. For a
demo, deny-list-by-default is fine.

`settings.local.json` ships a dev-only `MY_API_KEY=sk-local-dev-only`.
Even though it's gitignored ✓ and clearly a fixture, it'll trip every
secret scanner on earth if it ever leaks. Worth a comment that
explains this is *intentional* fixture data.

**First change:** add `gitleaks` to the secret-scanner stack, regex as
fallback.

### DevRel / engineering manager

The audience is engineers learning Claude Code. The **right artefact
for that audience** is a guided run-through of the `.claude/` directory
that takes ~30 minutes and produces working hooks, a populated wiki,
and a plan-driven feature.

The `DEMO_GUIDE.md` today is structured as a 10-minute walkthrough.
**Rename it `ONBOARDING.md` and re-pace it.** Section 1 (".claude
surface") becomes the meat; sections 4 (Web Audio) and 5 (testing) get

Self-paced reading is different from workshop pacing. A workshop has
a facilitator filling in gaps; a self-paced reader needs every
abstraction explained inline. Today's guide is workshop-pace. Make
both work — workshop-pace headlines, self-paced inline expansions.

The pre-rewrite-snapshot tag is the best slide of the demo. *"Claude
rewrote this entire repo and kept the original safe at one git tag."*
Lead with it.

**First change:** rename `DEMO_GUIDE.md` to `ONBOARDING.md`, restructure
around the `.claude/` surface as the core, with the app as substrate.

## Cross-cut answers to the four executive questions, summarised

1. **Onboarding-fit.** Yes, with two gaps: populate the wiki
   artefacts, add audit-loop integration tests.
2. **Wiki / anatomy / graph payoff visible.** Not yet — plumbing is
   there, content isn't. Run `/anatomy refresh` and `/setup graphify`
   in the next session and commit the output.
3. **Each .claude primitive right-sized.** Yes for hooks, settings,
   commands, agents, plans. **Rules need path-globs.** Skills could
   use one project-specific addition. CLAUDE.md should fork further
   into per-area files.
4. **Tests prove the harness works.** Unit-level yes (dispatcher
   correctness). Integration-level no — no test runs `/cc-audit` or
   `/anatomy refresh` against this repo and asserts something useful
   came out.
